# pootOS — архитектура

> Agent Operating System: песочница для агентов, ядро с планировщиком и лизисами
> ресурсов, контекст-граф вместо чата и системный агент, управляющий всем в рантайме.
>
> Документ фиксирует общую архитектуру, технологии и функционал. Язык бэкенда — Java 21
> (стиль Elegant Objects), фронтенд — React + TypeScript. Первая цель — защищённое
> приложение под Windows и macOS (Linux позже) с минимальным функционалом: запускать
> агентов и безопасно решать простую задачу.

---

## 0. Product Vision

Формат из EO-процесса (акторы, фичи, качество, ограничения). Мы держим **Thinking**-фазу:
здесь спека, кода ещё нет.

### 0.1 Акторы

1. **Owner** — человек-оператор (ArtemGet).
2. **System Agent** — мета-агент, конфигурирующий ОС в рантайме.
3. **Worker Agent** — исполнитель задачи (в MVP — ревью-агент).
4. **External systems** — GitHub (вебхуки/API), LLM-провайдеры.

### 0.2 Фичи по акторам (MVP, лимит по 3–4 фичи)

- **Owner:** поставить задачу (описание + артефакты); смотреть граф работ и контекста;
  отвечать на отложенные человеко-зависимые задачи; видеть ресурсы и таймауты.
- **System Agent:** добавить провайдера; добавить тул/MCP; определить шаблон агента;
  изменить политику — всё **без перезапуска процесса**.
- **Worker Agent:** стартовать в песочнице; читать/писать контекст-граф; порождать
  субагентов с **иной моделью**; производить артефакты и уроки.
- **Ревью-агент (MVP):** получать вебхук о PR → ревью по EO-скилу → публиковать ревью и
  метку в GitHub.

### 0.3 Качественные требования (измеримые)

- Агент **не может** прочитать/записать на хосте вне своего sandbox-root (проверяется
  негативным тестом: попытка должна падать).
- Ни два агента одновременно не удерживают один и тот же ресурс (`gpu:0`, `port:N`,
  `llm:rate:*`).
- От вебхука до старта ревью — < 30 с; ревью малого PR — < 10 мин.
- Падение агента не блокирует остальных; watchdog освобождает лизы в пределах TTL.
- Смена конфигурации (новый провайдер) применяется без рестарта процесса.
- Один агент = один durable actor; сотни агентов параллельно на virtual threads.

### 0.4 Ограничения

- Бэкенд Java 21, Maven, EO-стиль, гейты Qulice + jtcop + JaCoCo.
- Изоляция — Docker + gVisor (кроссплатформенно). Windows требует WSL2-бэкенд Docker.
- Web UI — React + TS; desktop (Kotlin Multiplatform/Compose) — позже.
- GitHub — один аккаунт ⇒ вердикт ревью выражается **меткой** (`approved`), не Approve.

## 2. Принципы

1. **Граф, а не транскрипт.** Единица состояния — типизированный узел со связями, не
   сообщение в чате.
2. **Изоляция по умолчанию.** Агент не наследует доступ к хосту; доступ — явный грант.
3. **Всё — ресурс с лизой.** Включая GPU, порты, сетевой egress и rate-limit провайдера.
4. **Durable by design.** Каждый агент — переживающий рестарт актор с журналом событий.
5. **Конфигурация — данные.** Меняется в рантайме, версионируется, откатывается.
6. **Fail fast, recover once.** Ошибки не глотаются; восстановление на верхнем уровне.
7. **Java core в стиле EO.** `final`, `private final`, конструкторы только присваивают,
   без `null`/статики/`instanceof`, поведение через декораторы. Гейты Qulice + jtcop.

## 5. Ядро (kernel)

### 5.1 Модель исполнения

- **Agent = durable actor.** Персистентное состояние: `AgentRecord{id, template, model,
  status, leases[], heartbeat, budget, currentTask, edgesToContext}`.
- Супервизия: корневой supervisor поднимает акторов; падение актора не роняет ядро.
- Параллелизм — **virtual threads (Loom)**: I/O (LLM, shell, GitHub) не блокирует поток
  планировщика. «Мейн-лупа-чата» нет вовсе — есть дерево задач и граф.
- **Event log** — append-only журнал (`SQLite` WAL + таблица событий). Восстановление
  состояния после рестарта = реплей журнала.

### 5.2 Resource Arbiter (R6)

- Ресурс — именованный: `gpu:0`, `port:8080`, `disk:/x`, `net:egress`, `llm:openai:rpm`.
- **Lease** = `{resource, owner, ttl, heartbeatAt, mode(shared|exclusive)}`.
- `acquire`:
  - свободен → выдаётся мгновенно;
  - занят exclusive → задача переходит в `queued-on-resource` (не виснет!), планировщик
    поднимет её при освобождении (приоритеты + FIFO).
- `renew` по heartbeat; истечение TTL → лиза освобождается.
- Дедлок невозможен по построению: assignment-порядок ресурсов + TTL + принудительный
  release при падении актора.

### 5.3 Таймауты, watchdog, бюджеты (R6)

- **Watchdog** (virtual thread-таймер): ищет протухшие лизы и молчащие heartbeat →
  помечает задачу `stalled`, освобождает лизы, эскалирует в repair-flow.
- **Budget** на задачу и на граф: `wallclock`, `tokens`, `vram`, `cost`. Превышение →
  задача убивается, пишется узел `Failure`, выделяется `Lesson`-кандидат.
- Правило из EO-плейбука: **никогда не запускать долгий foreground-билд** без таймаута и
  лог-файла; поллинг хвоста лога. Это применяется и к агентам песочницы.

### 5.4 Hot config (R16)

- Конфиг — узлы графа (`Config`), версионируются, content-addressed.
- `ConfigResolver` держит текущую версию; при появлении нового узла — атомарная подмена
  (декоратор). Провайдеры/тулы/шаблоны перечитываются лениво, процесс не рестартует.
- System Agent меняет конфиг мутацией узлов; ядро реагирует по подписке.

## 6. Песочница (R1, R15)

### 6.1 SPI

```java
interface Sandbox {
    Shell shell();       // PTY
    Workspace fs();      // контролируемая ФС
    Exec exec();         // запуск процессов
    void close();
}
```

### 6.2 Docker + gVisor (основной)

- Контейнер агента:
  - **non-root** пользователь; **read-only rootfs**; отдельный writable-слой (overlay);
  - **host FS не монтируется**; только проект — явным volume (по умолчанию `rw` в
    `/workspace`), плюс per-agent scratch;
  - `--runtime=runsc` (gVisor) для изоляции syscall-ов;
  - `--cap-drop=ALL`, `no-new-privileges`, seccomp/AppArmor-профиль;
  - лимиты `--memory`, `--pids-limit`, `--cpus`;
  - **сеть по умолчанию deny**: egress только через allowlist-прокси (GitHub API,
    провайдеры), либо `--network=none`.
- **Docker-сокет агенту недоступен** — иначе изоляция бессмысленна.
- Изолированный shell = PTY внутри контейнера, запущенный ядром.

### 6.3 Платформы

- **macOS / Linux:** Docker Engine в Linux-VM → `runsc` ставится в VM. Штатно.
- **Windows:** Docker Desktop с **WSL2-бэкендом**; `runsc` — в WSL2-дистрибутиве.
- **Fallback:** если `runsc` недоступен — hardened Docker (userns, cap-drop, no-network),
  факт деградации явно показывается в UI (не молча).

### 6.4 Секреты

- Хранилище: Windows Credential Manager / macOS Keychain (через Java).
- Секрет подаётся **на границе песочницы** (secret file/переменная), **никогда** в
  контекст-граф, промпт или лог. Централизованная редакция логов.
- GitHub-токен — только для GitHub-интеграции; агенту выдаётся минимально необходимый
  доступ (или проксируется через ядро, чтобы токен вообще не попадал в контейнер).

## 7. Контекст-граф (R7, R8, R10, R12)

### 7.1 Узлы

`Task`, `Decision`, `Evidence`, `Artifact`, `Failure`, `Lesson`, `HumanQuestion`, `Summary`,
`Review`, `Finding`, `Config`.

### 7.2 Рёбра

`depends_on`, `derived_from`, `supersedes`, `invalidated_by`, `taught_by`, `addresses`,
`produces`.

### 7.3 Content-addressing и хранение

- Узел адресуется SHA-256 канонического JSON. Хранение: **SQLite** (узлы, рёбра, события)
  + blob-store для артефактов. Портативно, без сервера.
- Идемпотентная запись: одинаковый узел = тот же адрес (важно для sync, R11).

### 7.4 Срезы и чтение

- Агент читает не транскрипт, а **срез**: `slice(taskId)` — замыкание узлов по рёбрам
  `derived_from`/`depends_on`/`addresses` до заданной глубины, с приоритетом свежих и
  релевантных. Срез — вход промпта агента.
- Запись: `attach(node, edges[])`.

### 7.5 Компакция и lessons (R10)

- `Summary`-узел ссылается на источники (`derived_from`); оригиналы сохраняются/архивируются
  ⇒ **сжатие без потери провенанса**. Переход между проектами/сессиями сохраняет уроки.
- **`Lesson`** (журнал косяков, first-class):
  - поля: `trigger` (glob по тегам задач / сигнатурам ошибок), `advice`, `validity`,
    `sourceFailure`, `confidence`;
  - перед каждым шагом агент запрашивает релевантные уроки; совпавшие внедряются в промпт
    как **ограничения**;
  - успех («внёс правку — заработало») фиксируется `Lesson` и переиспользуется в
    будущих задачах ⇒ решается боль «успех проёбан при смене задачи».

### 7.6 Спасение контекста умершего агента (R8)

- Падение/stall → поддерево помечается `stalled`.
- **Repair-flow**: repair-агент наследует **upstream-контекст по рёбрам** (решения,
  доказательства, артефакты), а не сырой диалог, и продолжает с точки разрыва.
- Repair-агент может иметь иную модель, чем сдохший.

## 8. Таксономия human-зависимых задач (R9)

- Узел `HumanQuestion` с полями: `level` (L0 авто · L1 уведомить · L2 спросить · L3 только
  человек), `requiredCapability`, `deadline`, `escalationPolicy`.
- Блокирующая задача переводится в **deferred-очередь**, независимые ветки DAG
  **продолжают исполняться**. «Обходить важные и не останавливать работу» — свойство
  планировщика, не агента.
- В UI — отдельная очередь с уровнями и дедлайнами.

## 9. System Agent (R2, R5)

Тот же рантайм агента, но с привилегированным набором операций:

- `define_provider(...)`, `define_tool(...)`, `define_mcp(...)`,
  `define_agent_template(...)`, `define_skill(...)`, `set_policy(...)`,
  `define_human_task_level(...)`.
- Каждая операция = запись узлов `Config`/`Template`; ядро применяет hot-reload.
- «Динамически рулить» = System Agent мутирует граф, kernel реагирует. Никаких рестартов.

## 10. Агент-рантайм (R3, R14, R15)

- **Agent Template** — декларация: системный промпт, набор скилов, разрешённые тулы, тип
  песочницы, дефолтная `ModelRef`, бюджеты, ресурсные требования.
- **Skills** — загружаемые рецепты (в т.ч. EO-review, см. §12); авторинг по пайплайну
  `programming-philosophy-skill` (интервью → извлечение → свёрнутый rulebook).
- **Tools / MCP** — Java MCP-клиент; тулы выдаются агенту по шаблону.
- **Субагенты (R14):** `spawn(template, ModelRef)`; `ModelRef` субагента может отличаться
  от родителя — штатно. Родитель не блокируется: субагент — отдельный актор.
- Шаг агента: `read slice → query lessons → act (tool/shell/LLM) → attach nodes → renew
  lease`. Каждый шаг идемпотентен и логируется.

---

## 11. Провайдеры (R3)

- SPI `ModelProvider { complete(request): response }` + реестр провайдеров.
- Адаптеры MVP: OpenAI-совместимый (base URL/ключ), Anthropic, локальный (Ollama/иной).
- Per-agent `ModelRef{provider, model, params}`; rate-limit провайдера — ресурс с лизой
  (`llm:openai:rpm`), что защищает от троттлинга при параллельных агентах.

## 12. GitHub-интеграция и ревью-агент (MVP-задача)

### 12.1 Поток

```
GitHub webhook (pull_request: opened|synchronize|reopened)
        │  HMAC-подпись проверяется ядром
        ▼
ReviewTask (узел Task) ──► lease(net:egress, llm:*)
        │
        ▼
Ревью-агент в песочнице:
  1. resolve repo/PR; прочитать связанный issue (PR должен закрывать РОВНО его)
  2. получить diff (GitHub API через ядро; токен не в контейнере)
  3. EO-проверки (см. §12.2)
  4. если нужно — фоновый `mvn -Pqulice -Pjtcop` в песочнице с таймаутом и логом
  5. опубликовать ревью + строчные комментарии; развести nit vs follow-up
  6. применить метку `approved`/`needs-review`
  7. записать узлы Review/Finding/Lesson
```

### 12.2 Конвенции ревью (из EO-skill + практики `teleroute`)

- **Correctness** — изменение делает то, что просит issue; edge-cases.
- **Tests** — тест, воспроизводящий баг (падал до), один `assertThat` на тест, Hamcrest,
  `final` класс, без полей, имя `*Test`.
- **Style/EO** — `final` классы, `private final` поля, без static/`null`/`instanceof`
  (кроме `equals`), без слепых кастов.
- **Process** — ветка названа по issue, коммиты начинаются с `#<issue>`, один concern,
  без перезаписи истории.
- **Gates** — Qulice 0.36 + jtcop зелёные; CI прочитан через GitHub MCP (не гонять
  долгий foreground-билд вслепую).
- **Триаж комментариев:**
  - **nit** → автор правит в этом же PR (доп. коммит с тем же тикетом);
  - **крупное** → отдельный issue `Follow-up: #NNN`, PR не растёт;
  - ответить на **каждый** комментарий; резолвить свои треды.
- **Один аккаунт:** `Approve` невозможен ⇒ **метка — это вердикт**; не писать
  мета-комментарии про ограничения платформы.
- **Формат ответа:** `verdict / checks / actions / remaining`.
- Источники конвенций: `references/11-reviewer-playbook.md`, `references/07-process.md`
  EO-скила и наблюдаемые PR/issue `ArtemGet/teleroute` (issue-first с минимальным
  воспроизведением, `Closes #N`, What/Why/How/Test plan, gate, PDD-пазлы).

### 12.3 Безопасность

- Проверка HMAC вебхука; allowlist репозиториев.
- Токен GitHub — в хранилище секретов; по возможности прокидывается **через ядро**, чтобы
  в контейнер агента не попадал вовсе.
- Ревью-агент не имеет доступа к `push`/`merge` — только чтение и комментарии/метки.

## 13. UI (R4, R12)

- **Граф контекста** (React Flow): узлы по типам/статусам, типизированные рёбра, фильтры.
- **DAG работ**: зависимости задач, критический путь, статусы.
- **Дашборд ресурсов**: лизы (кто держит `gpu:0`/порт), heartbeat, TTL, бюджеты, стоимость.
- **Human-очередь**: `HumanQuestion` по уровням L0–L3, дедлайны, эскалации.
- **Карточка агента**: template, `ModelRef`, heartbeat, лизы, шаги, стрим событий.
- Взаимодействие — **композиция узлов на канвасе**, не чат. Live-updates по WebSocket.
- Frontend: React + TS + Vite + React Flow. Позже — desktop на Kotlin Multiplatform/Compose
  поверх того же `pootos-ui-api`.

## 14. Синхронизация между машинами (R11) — дизайн

- Контекст-граф = append-only лог; узлы content-addressed ⇒ слияние = объединение множеств
  (конфликтов по узлам нет; одинаковый узел = один адрес).
- Транспорт (варианты, выбрать позже): git-репозиторий data-dir · Syncthing · небольшой
  sync-сервер поверх того же лога.
- `HumanQuestion`/`Config` — точки потенциального конфликта; решаются CRDT-семантикой
  (LWW по версии или явное разрешение).
- Перенос «сервер → сервер»: переносится лог + blob-store; агент восстанавливается реплеем.

| Слой | Выбор | Почему |
|---|---|---|
| Бэкенд | Java 21 (Loom), Maven, EO | virtual threads = сотни агентов дёшево; EO-стиль и гейты |

## 16. Безопасность (что гарантируем)

- **ФС:** агент видит только смонтированный `/workspace` и scratch; host вне — недоступен.
- **Процессы:** изоляция syscall-ов gVisor; без `--privileged`; cap-drop ALL.
- **Сеть:** default-deny; egress по allowlist через прокси.
- **Docker:** сокет только у ядра, не у агентов.
- **Секреты:** keychain; вне контекста/промптов/логов; редакция.
- **GitHub:** HMAC вебхука, allowlist, минимальные права (read + comment/label).
- **Аудит:** все действия — события в журнале (кто, что, когда, под какой лизой).

## 18. Roadmap / MVP-срез

1. **Thinking** (сейчас): этот документ. ✅
2. **Building — MVP (Win/macOS):**
   1. `kernel`: акторы на virtual threads + event log + leases + watchdog + budgets.
   2. `context`: узлы/рёбра/срезы/компакция + `Lesson`.
   3. `sandbox` + `sandbox-docker` (gVisor, изолированный shell, `/workspace`).
   4. `providers`: OpenAI-compat + Anthropic; `ModelRef` per-agent.
   5. `agent`: шаблоны, скилы, субагенты с чужими моделями.
   6. `github` + ревью-агент по EO-скилу.
   7. `ui-api` + минимальный Web UI (граф + дашборд ресурсов).
   8. e2e: вебхук PR → ревью опубликовано под меткой.
3. **Fixing:** стабилизация под нагрузкой, негативные тесты изоляции.
4. **Using:** багфиксы, расширение скилов.

**Definition of Done MVP:** негативный тест изоляции зелёный; два параллельных агента не
делят ресурс; вебхук → ревью EO-конвенциям соответствует; конфиг-смена без рестарта;
пакет ставится и запускается на Windows и macOS.

## 19. Риски и открытые вопросы

- **gVisor на Docker Desktop (Win/macOS):** проверить доступность `runsc` в WSL2/Linux-VM;
  при отсутствии — явная деградация до hardened Docker.
- **Качество LLM-ревью:** митигируется строгим EO-скилом + `Lesson`-журналом.
- **Стоимость/латентность ревью:** бюджеты и allowlist; дифференциация модели по размеру PR.
- **Durability single-node:** event log + SQLite; далее — вынести лог.
- **Синхронизация:** отложена, но content-addressing заложен с самого начала.
