# pootOS — архитектура

> Agent Operating System: песочница для агентов, ядро с планировщиком и лизами
> ресурсов, контекст-граф вместо per-task чата и системный агент, управляющий всем
> в рантайме.
>
> Документ фиксирует архитектуру, технологии и функционал. Язык бэкенда — Java 25
> (Elegant Objects), фронтенд — React + TypeScript. Первая цель — защищённое приложение
> под Windows и macOS (Linux позже) с минимальным функционалом: безопасно запускать
> агентов и решать простую задачу (EO-ревью PR).
>
> **Языки документации:** ru (этот файл — канон) · en (`ARCHITECTURE.en.md`) ·
> zh-CN (`ARCHITECTURE.zh-CN.md`). Переводы ведутся отдельным агентом, актуальность
> периодически проверяется агентом-аудитором (см. §22).
>
> ru (этот файл) · [en](ARCHITECTURE.en.md) · [zh-CN](ARCHITECTURE.zh-CN.md)

## 0. Product Vision

Формат из EO-процесса (акторы, фичи, качество, ограничения). Фаза **Thinking**: спека.

### 0.1 Акторы

1. **Owner** — человек-оператор (ArtemGet).
2. **System Agent** — мета-агент; единственный собеседник Owner через главный чат.
3. **Worker Agent** — исполнитель задачи (в MVP — ревью-агент).
4. **External systems** — GitHub (вебхуки/API), LLM-провайдеры, MCP-серверы.

### 0.2 Модель взаимодействия Owner ↔ система

- **Один главный чат — навсегда.** Он не про задачу; он про управление ОС. Через него
  Owner:
  - ставит задачи («что нужно сделать») и отдаёт их **System Agent**;
  - даёт правки/корректировки;
  - читает отчёты System Agent.
- **System Agent принимает указание и раздаёт его дальше, не блокируя свой луп.**
  Системный агент — координатор: создаёт узлы `Task`, подбирает агентов/шаблоны,
  выдаёт ресурсы, следит за прогрессом. Пока агенты работают, он остаётся отзывчивым.
- **Вся работа — не в чате, а на канвасе** (задачи, артефакты, агенты).
- Функции чата строго ограничены: старт, указания/правки, отчёты. Никакого
  «чата на задачу».

### 0.3 Канвас и зоны внимания

Канвас — основное рабочее пространство. Три зоны по потребности человека во внимании:

| Зона | Смысл | Пример |
|---|---|---|
| 🔴 **RED** | Нужно решение человека; работа ветки заблокирована | запрос доступа к токену/секрету; запрос маунта; неоднозначное требование; исчерпан бюджет; подозрение на необратимое действие |
| 🟡 **YELLOW** | Человеку желательно посмотреть, но блокировки нет | результат на грани, несколько вариантов, деградация изоляции |
| 🟢 **GREEN** | Агенты справляются сами, вмешательство не нужно | обычное выполнение |

- **Задачи переезжают между зонами** при изменении состояния (планировщик/агенты
  переносят карточку).
- В зонах — **карточки**. С карточки можно провалиться внутрь: увидеть, что делают
  агенты, их шаги, артефакты, и **написать прямо в карточку** (правка/уточнение).

### 0.4 Карточка ≠ Агент

- **Карточка** — задача или артефакт. Над одной карточкой могут работать **несколько
  агентов** (например, исполнитель + ревьюер + repair).
- **Агент** — отдельная сущность со своими: скилами, доступом к MCP, доступом к shell,
  набором примаунченных папок, моделью(ями), шаблоном.
- Отдельные представления: **«сейчас работают»** и **«все агенты»**.

### 0.5 Фичи по акторам (MVP, лимит по 3–4)

- **Owner:** поставить задачу через чат; видеть зоны/карточки/агентов; отвечать на
  RED/YELLOW; видеть ресурсы и принимать решения (оптимизировать / остановить /
  перезапустить зависших агентов).
- **System Agent:** создать/распределить задачи; добавить провайдера, тул, MCP, шаблон
  агента; конфигурировать **себя и само приложение pootOS через агентов**; менять политики
  — всё **без перезапуска процесса**.
- **Worker Agent:** стартовать в песочнице; читать/писать контекст-граф; порождать
  субагентов с **иной моделью**; запрашивать маунты; производить артефакты и уроки.
- **Ревью-агент (MVP):** вебхук о PR → EO-ревью → публикация ревью и метки в GitHub.

### 0.6 Качественные требования (измеримые)

- Агент **не может** читать/писать на хосте вне своего sandbox-root (негативный тест).
- Ни два агента одновременно не удерживают один ресурс (`gpu:0`, `port:N`, `llm:rate:*`).
- Вебхук → старт ревью < 30 с; ревью малого PR < 10 мин.
- Падение агента не блокирует остальных; watchdog освобождает лизы в пределах TTL.
- Смена конфигурации (новый провайдер) применяется без рестарта процесса.
- Один агент = один durable actor; сотни агентов параллельно на virtual threads.

### 0.7 Ограничения

- Бэкенд Java 25, Maven, EO-стиль, гейты Qulice 0.36 + jtcop + JaCoCo/PIT.
- Изоляция — Docker + gVisor (`runsc`). Windows требует WSL2-бэкенд Docker.
- Web UI — React + TS; desktop (Kotlin Multiplatform/Compose) — позже.
- GitHub — один аккаунт ⇒ вердикт ревью выражается **меткой** (`approved`), не Approve.

## 2. Принципы

1. **Граф, а не транскрипт.** Единица состояния — типизированный узел со связями.
2. **Изоляция по умолчанию.** Доступ к хосту/секретам — явный грант.
3. **Всё — ресурс с лизой.** GPU, порты, egress, rate-limit провайдера.
4. **Durable by design.** Агент переживает рестарт (event-sourced).
5. **Конфигурация — данные.** Меняется в рантайме, версионируется, откатывается.
6. **Секреты неприкосновенны.** Агент может писать конфиг, но не читать токены.
7. **Fail fast, recover once.**
8. **Java core в стиле EO.** `final`, `private final`, конструкторы только присваивают,
   без `null`/статики/`instanceof`, поведение через декораторы. Гейты Qulice + jtcop.

## 5. Ядро (kernel)

### 5.1 Модель исполнения

- **Agent = durable actor.** Состояние: `AgentRecord{id, template, modelRef, status,
  leases[], heartbeat, budget, currentCard, edgesToContext}`.
- Супервизия: корневой supervisor; падение актора не роняет ядро.
- Параллелизм — **virtual threads (Loom)**: I/O (LLM, shell, GitHub) не блокирует
  планировщик. Мейн-лупа-чата нет — есть DAG задач и граф.
- **Event log** — append-only (`SQLite` WAL + таблица событий); восстановление — реплей.

### 5.2 Resource Arbiter (R6)

- Ресурс именованный: `gpu:0`, `port:8080`, `disk:/x`, `net:egress`, `llm:openai:rpm`.
- **Lease** = `{resource, owner, ttl, heartbeatAt, mode(shared|exclusive)}`.
- `acquire`: свободен → мгновенно; занят exclusive → задача в `queued-on-resource`
  (не виснет), планировщик поднимет при освобождении (приоритеты + FIFO).
- `renew` по heartbeat; истечение TTL → release. Дедлок невозможен по построению
  (порядок захвата + TTL + принудительный release при падении).

### 5.3 Таймауты, watchdog, бюджеты, операторские решения (R6)

- **Watchdog** ловит протухшие лизы и молчание heartbeat → `stalled`, освобождает лизы,
  эскалирует в repair-flow.
- **Budget** на задачу/граф: `wallclock`, `tokens`, `vram`, `cost`. Превышение → kill,
  узел `Failure`, `Lesson`-кандидат.
- **Дашборд ресурсов** показывает: доступные ресурсы, кто держит лизы, TTL, зависших.
  Owner/System Agent может **оптимизировать / остановить / перезапустить** агента.
- Долгие foreground-билды не запускаются вслепую: таймаут + лог-файл + поллинг хвоста.

### 5.4 Зоны (R9)

- Планировщик переводит карточку между `RED`/`YELLOW`/`GREEN` по правилам и по событиям
  агентов (запрос доступа, исчерпание бюджета, деградация изоляции и т.п.).

### 5.5 Hot config (R16, R18)

- Конфиг — узлы графа (`Config`), версионируются, content-addressed.
- `ConfigResolver` атомарно подменяет версию (декоратор); провайдеры/тулы/шаблоны
  перечитываются лениво, без рестарта.
- System Agent меняет конфиг мутацией узлов; ядро реагирует по подписке.
- **Разделение прав:** запись конфигов разрешена; **чтение секретов — нет** (см. §12).

## 6. Песочница (R1, R15)

### 6.1 SPI

```java
interface Sandbox {
    Shell shell();       // PTY
    Workspace fs();      // контролируемая ФС
    Exec exec();         // запуск процессов
    void close();
}
```

### 6.2 Docker + gVisor (основной)

- Контейнер агента:
  - **non-root**; **read-only rootfs**; отдельный writable-слой (overlay);
  - **host FS не монтируется**; только явно одобренные маунты проекта;
  - `--runtime=runsc` (gVisor);
  - `--cap-drop=ALL`, `no-new-privileges`, seccomp/AppArmor;
  - лимиты `--memory`, `--pids-limit`, `--cpus`;
  - **сеть default-deny**: egress только через allowlist-прокси (GitHub API, провайдеры).
- **Docker-сокет агенту недоступен.**
- Изолированный shell = PTY в контейнере, запущенный ядром.

### 6.3 Платформы

- **macOS/Linux:** Docker Engine в Linux-VM → `runsc`. Штатно.
- **Windows:** Docker Desktop с **WSL2-бэкендом**; `runsc` — в WSL2-дистрибутиве.
- **Fallback:** нет `runsc` → hardened Docker; факт деградации **явно** в UI (не молча) и
  переводит затронутую карточку в 🟡 YELLOW.

### 6.4 Проект и маунты (R12)

- **`Project` — логическая сущность, не привязан к одной папке.** Один проект может
  включать 1, 2 или больше примаунченных директорий реальной ОС.
- **Маунт по запросу агента, решение — за человеком.** Поток:
  1. агент пишет узел `MountRequest{path, mode(ro|rw), reason}`;
  2. карточка запроса едет в 🔴 RED;
  3. человек одобряет/отклоняет;
  4. при одобрении ядро добавляет маунт в контейнеры соответствующих агентов.
- По умолчанию маунт `ro`; `rw` требует явного подтверждения.
- Один агент может касаться нескольких проектов; проекты шарят уроки (см. §7.5), но
  разделяют артефакты/маунты.

## 7. Контекст-граф (R7, R8, R10, R12)

### 7.1 Узлы

`Task`, `Decision`, `Evidence`, `Artifact`, `Failure`, `Lesson`, `HumanQuestion`, `Summary`,
`Review`, `Finding`, `Config`, `MountRequest`.

### 7.2 Рёбра

`depends_on`, `derived_from`, `supersedes`, `invalidated_by`, `taught_by`, `addresses`,
`produces`.

### 7.3 Content-addressing и хранение

- Узел адресуется SHA-256 канонического JSON. Хранение: **SQLite** (узлы, рёбра, события)
  + blob-store для артефактов. Портативно, без сервера.
- Идемпотентная запись: одинаковый узел = тот же адрес (основа sync, R11).

### 7.4 Срезы и чтение

- Агент читает **срез**: `slice(taskId)` — замыкание по рёбрам
  `derived_from`/`depends_on`/`addresses` до заданной глубины, приоритет свежих и
  релевантных. Срез — вход промпта агента.
- Запись: `attach(node, edges[])`.

### 7.5 Компакция и lessons (R10)

- `Summary`-узел ссылается на источники (`derived_from`); оригиналы сохраняются/архивируются
  ⇒ сжатие **без потери провенанса**. Уроки переживают смену сессии/проекта.
- **`Lesson`** (журнал косяков, first-class):
  - `trigger` (glob по тегам задач / сигнатурам ошибок), `advice`, `validity`,
    `sourceFailure`, `confidence`;
  - перед шагом агент запрашивает релевантные уроки; совпавшие внедряются в промпт как
    **ограничения**;
  - успех («внёс правку — заработало») фиксируется `Lesson` и переиспользуется ⇒ решается
    боль «успех теряется при смене задачи».

### 7.6 Спасение контекста умершего агента (R8)

- Падение/stall → поддерево `stalled`.
- **Repair-flow:** repair-агент наследует upstream-контекст по рёбрам (решения,
  доказательства, артефакты), а не сырой диалог, и продолжает с точки разрыва.
- Repair-агент может иметь иную модель.

## 8. Таксономия human-зависимых задач (R9)

- `HumanQuestion{level, requiredCapability, deadline, escalationPolicy}`:
  - **L0** авто · **L1** уведомить · **L2** спросить · **L3** только человек.
- Блокирующая задача → deferred-очередь; независимые ветки DAG **продолжают**.
- Отображение через зоны: L2/L3 → 🔴; «желательно посмотреть» → 🟡.

## 9. System Agent (R2, R5, R17, R18)

Тот же рантайм агента, привилегированный набор операций:

- `define_provider`, `define_tool`, `define_mcp`, `define_agent_template`, `define_skill`,
  `set_policy`, `define_human_task_level`, `create_task`, `assign_agent`, `move_zone`.
- Каждая операция = запись узлов `Config`/`Template`/`Task`; ядро применяет hot-reload.
- **Принимает указания из главного чата и раздаёт их, не блокируя свой луп.**
- **Самоконфигурация:** System Agent конфигурирует себя и приложение pootOS **через
  агентов** — но **не читает секреты** (см. §12).

## 10. Агент-рантайм (R3, R14, R15)

- **Agent Template** — декларация: системный промпт, скилы, разрешённые тулы/MCP, тип
  песочницы, дефолтный `ModelRef`, бюджеты, ресурсные требования, разрешённые маунты.
- **Skills** — загружаемые рецепты (в т.ч. EO-review, §13); авторинг по пайплайну
  `programming-philosophy-skill`.
- **Tools / MCP** — Java MCP-клиент; удобное подключение; тулы выдаются по шаблону.
- **Субагенты (R14):** `spawn(template, ModelRef)`; `ModelRef` субагента может отличаться
  от родителя. Родитель не блокируется: субагент — отдельный актор.
- Шаг агента: `read slice → query lessons → act → attach nodes → renew lease`. Каждый шаг
  идемпотентен и логируется.
- Настройка агента — **руками или через System Agent**.

## 12. Безопасность конфигурации и секретов (R18)

Ключевое разделение («заполнить конфиг — да, получить токен — нет»):

- **Config-write:** System Agent/агенты могут создавать и править конфиги (провайдеры,
  тулы, MCP, шаблоны) — это данные графа, не секреты.
- **Secret-read:** доступ к токенам/ключам запрещён агентам. Хранилище — Windows
  Credential Manager / macOS Keychain.
- **Поток при необходимости секрета:**
  1. агент формирует `SecretRequest` — карточка едет в 🔴 RED;
  2. **человек** вводит/подтверждает секрет (никогда — агент);
  3. секрет подаётся **на границе песочницы** (secret file/env), **не** в контекст-граф,
     промпт или лог (централизованная редакция);
  4. `Config` получает **ссылку** на секрет (`SecretRef`), а не значение.
- **GitHub-токен:** по возможности прокидывается **через ядро** (агент не видит значение);
  альтернатива — `SecretRef` на границе песочницы. Решение — ADR-005.

## 13. GitHub-интеграция и ревью-агент (MVP-задача)

### 13.1 Поток

```
GitHub webhook (pull_request: opened|synchronize|reopened)
        │  HMAC-подпись проверяется ядром
        ▼
Card(Task) ──► lease(net:egress, llm:*) ──► зона GREEN
        │
        ▼
Ревью-агент в песочнице:
  1. resolve repo/PR; прочитать связанный issue (PR закрывает РОВНО его)
  2. получить diff (GitHub API через ядро; токен не в контейнере)
  3. EO-проверки (§13.2)
  4. при необходимости — фоновый `mvn -Pqulice -Pjtcop` в песочнице (таймаут + лог)
  5. опубликовать ревью + строчные комментарии; развести nit vs follow-up
  6. применить метку `approved`/`needs-review`
  7. записать узлы Review/Finding/Lesson
```

### 13.2 Конвенции ревью (EO-skill + практика `teleroute`)

- **Correctness** — делает то, что просит issue; edge-cases.
- **Tests** — воспроизводящий тест (падал до), один `assertThat` на тест, Hamcrest, `final`
  класс, без полей, имя `*Test`.
- **Style/EO** — `final` классы, `private final` поля, без static/`null`/`instanceof`
  (кроме `equals`), без слепых кастов.
- **Process** — ветка по issue, коммиты с `#<issue>`, один concern, без перезаписи истории.
- **Gates** — Qulice 0.36 + jtcop зелёные; CI читать через GitHub MCP (не гонять долгий
  foreground-билд вслепую).
- **Триаж:** nit → правка в этом же PR; крупное → отдельный issue `Follow-up: #NNN`;
  ответить на каждый комментарий; резолвить свои треды.
- **Один аккаунт:** `Approve` невозможен ⇒ **метка — вердикт**; без мета-комментариев.
- **Формат ответа:** `verdict / checks / actions / remaining`.
- Источники: `references/11-reviewer-playbook.md`, `references/07-process.md` EO-скила;
  PR/issue `ArtemGet/teleroute` (issue-first с минимальным репро, `Closes #N`,
  What/Why/How/Test plan, gate, PDD-пазлы).

## 17. Безопасность (что гарантируем)

- **ФС:** агент видит только одобренные маунты; host вне — недоступен.
- **Процессы:** изоляция syscall-ов gVisor; без `--privileged`; cap-drop ALL.
- **Сеть:** default-deny; egress по allowlist через прокси.
- **Docker:** сокет только у ядра.
- **Секреты:** keychain; **агент не читает**; только `SecretRef`; редакция логов.
- **GitHub:** HMAC вебхука, allowlist, минимальные права (read + comment/label).
- **Аудит:** все действия — события (кто, что, когда, под какой лизой).

## 19. Завод разработки (как создаётся pootOS)

Роли (все — агенты, кроме Owner):

- **Orchestrator** (главный агент): описывает архитектуру, режет на подзадачи, ведёт треки,
  отчитывается Owner; минимально валидирует. **Сам код не пишет.**
- **Coding subagent**: реализует одну подзадачу в изолированном воркспейсе; обязан оставить
  тест(ы); соблюдает EO + гейты.
- **Review subagent**: независимо ревьюит; **при успехе — мержит** (см. §19.2).
- **Docs subagent**: держит `ru/en/zh-CN` в синхроне.
- **Docs-auditor agent**: периодически проверяет актуальность документации.

### 19.1 Поток

```
Owner → главный чат → Orchestrator
Orchestrator → подзадача → Coding subagent (локальный клон, ветка)
        → build `mvn --errors --batch-mode clean install -Pqulice -Pjtcop` (JAVA_HOME=25)
        → PR (через GitHub MCP)
        → Review subagent (по EO-плейбуку)
        → если ОК: Review subagent мержит; иначе: замечания → новый цикл
Orchestrator → трек + отчёт Owner
```

### 19.2 Правила

- Один concern на PR; маленькие PR; тест на каждое поведение/баг.
- Гейты `Qulice 0.36 + jtcop + JaCoCo` обязательны; зелёный build — условие мержа.
- Ревьюер **мержит только при успехе** (в один аккаунт — метка как вердикт).
- Без перезаписи истории; коммиты со ссылкой на issue (`#<issue>`).
- Код пишут **только субагенты**; Orchestrator — спеки/разбиение/треки/отчёты.

## 21. Риски и открытые вопросы

- **Локальный push:** нет неинтерактивного токена ⇒ MCP; при желании — PAT (§22).
